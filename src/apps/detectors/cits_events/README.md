# R10 — события по замерам ЦИТС относительно техрежима

Перенос скрипта автора правила `cits_events.py` (версия 2026-09-18.5) в
детекторы. Пороги автора предварительные: ретро-проверка не проведена.

## Что делает

На каждую дату фиксации (закрытые местные сутки) каждая скважина ЖМГ с
замерами за 75 суток находится ровно в одном состоянии:

| № | Событие | Условие | Куда |
|---|---|---|---|
| 1 | Отклонение, свежее | Qж ≤ 0.7 × техрежим на 3 замерах подряд, серия ≤ 14 сут, до неё норма | эпизод, warning |
| 2 | Нулевые замеры | 2 замера подряд ≤ 0.5 м³/сут, + признак СУ | эпизод, alarm («неустойчивые» и периодика — warning) |
| 3 | Замер устарел | последний замер старше 7 сут (периодическая эксплуатация — 14), + признак СУ | срез, раздел `measure_request` |
| 4 | Пустой замер | в последнем замере Qж пуст | срез, `data_quality` |
| — | Сервисный перечень | хроника вниз/вверх, «ранее выше плана», нет/устарел техрежим, простой в ABAI при работающей СУ | срез, `data_quality` |

Скважины в простое ABAI не оцениваются: простой через сутки и открытый
вырезают свои дни из ряда, простой внутри суток идёт в примечание.

`rule.py` — чистая функция, перенос `evaluate()` с тем же порядком проверок.
Соответствие скрипту проверено 28.09.2026 прогоном обеих реализаций на данных
прода за 20.08, 01.09, 10.09, 18.09 и 28.09 (3 156 оценок, 210 событий,
280 строк сервиса): расхождений нет.

## Отличия от скрипта

Решения владельца от 28.09.2026:

- порог «замер устарел» для периодической эксплуатации — 14 суток
  (`STALE_D_PERIODIC`), для остальных 7;
- событие 3 делится по признаку СУ, как событие 2. На 28.09 из 15 устаревших
  у 12 СУ стояла при статусе «В работе»/«Периодическая» — действие по ним не
  замер, а разбор, почему скважина стоит.

Технические:

- дата фиксации — закрытые сутки (у автора — сегодня, неполные), поэтому
  окно СУ «последние 3 суток» включает саму дату фиксации;
- Qm_liq не зеркалится: в ЦИТС ЖМГ Qv и Qm пусты одновременно; пустой Qv
  у настоящих скважин за всю историю — один случай (BLG_0080, 02.12.2023);
- статусы переводятся из UTC в местные сутки через `TZ_NAME`, у автора —
  `+ 5 часов` (для Атырау одно и то же);
- скважины с буквенными номерами не отбрасываются: ключ у нас — скважина,
  а не пара «месторождение + номер».

## Эпизод

Один сигнал на скважину — `liquid_loss`. Правило суточное и без памяти,
эпизод — с памятью (`services/episode.py`): закрывается по явной причине,
а не по первому дню без события:

- `idle` — на скважине поставили простой в ABAI;
- `stale` — замер устарел, подтвердить нечем;
- `chronic` — серия ушла в хронику (старше 14 суток);
- `recovered` — последний учтённый замер в норме.

Пока последний замер плохой (ноль или за порогом), эпизод держится открытым,
но не дольше 14 суток без подтверждения. Переход отклонения в нули —
эскалация того же эпизода.

ИИ-заключений по R10 нет: в `conclusion/catalog.py` для него только причина
(для ведомости), рекомендаций нет — нужны формулировки технолога.

## Данные

- замеры — `telemetry_well` (загрузчик WinCC; ZNT→ZHT и перечитка 7 суток);
- техрежим — `telemetry_tech_regime`;
- статусы — `wells_well_status` (копия `emg.well_status`, раз в час);
- СУ — регистр 1998 в `telemetry_sdmo_fc_data`, станция по коду с синонимом
  ZBN/ZBR, только по запрошенным правилом суткам.

## Запуск

Celery `detectors.cits_events.run_incidents`, beat 06:30 местного, за вчера.
Курсор НГДУ (`detectors_cursor`, `entity_id` = ABAI id НГДУ) — пропущенные
сутки догоняются по порядку, не больше 7 за прогон.

Ежечасно в :40 тот же таск с `intraday=True` считает сегодняшние неполные
сутки: сигнал появляется в тот же день. По неполным суткам эпизоды только
открываются и повышаются — закрытие, срез и курсор остаются утреннему
расчёту; до него (пока вчерашние сутки не рассчитаны) прогон пропускается.

## Суточная ведомость

R10 входит в общую ведомость (`services/daily_sheet`) и письмо по НГДУ: сборка
07:30, рассылка 07:50, только по НГДУ из `TARGET_NGDU_IDS` (по остальным —
404 и без вложения). Отличия от R2/R9: охват — скважины с замерами ЦИТС
(`coverage.source = cits`), а не станции СДМО; раздел «Запросить замер» из
среза `stale`; вероятность — 50 % у всех строк (модели уверенности нет),
рекомендация — «наблюдение» с основанием.

```bash
cd src && python -m apps.detectors.cits_events.tasks.run_incidents.run_incidents
cd src && python -m apps.detectors.cits_events.tasks.run_incidents.run_incidents --date 2026-09-27
cd src && python -m apps.detectors.cits_events.tasks.run_incidents.run_incidents --intraday
```

API среза: `GET /detectors/v1/findings?section=measure_request|data_quality`
(без даты — последняя). Эпизоды — общий `GET /detectors/v1/incidents`.

## Первый запуск на среде

1. `alembic upgrade head`.
2. Копия статусов: `python -m apps.wells.tasks.load_well_status.load_well_status`
   (первая загрузка ~840 тыс. строк).
3. История ZHT в замерах:
   `python -m apps.telemetry.tasks.load_telemetry.load_wincc --ngdu ZHMG --since 2023-11-01`.
4. Дальше — по расписанию.
