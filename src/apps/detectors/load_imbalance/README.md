# Детектор перекоса нагрузки — правило R9

Суточное правило по фонду ШГН (`type_1900 = 1`). Ловит уход полезной нагрузки
со штанг: утечку в клапанах, износ пары плунжер–цилиндр, неполное заполнение
насоса, срыв плунжера.

## Что считает

По суточному распределению момента на валу (регистр 1991, снимки при
работающем приводе):

```
K = |P5| / P95
```

`P95` — характерный рабочий пик (ход вверх, поднимаем штанги со столбом
жидкости), `P5` — характерный обратный, генераторный пик (ход вниз,
противовесы раскручивают привод). Когда нагрузка уходит, баланс ломается с
двух сторон разом: рабочие пики падают, обратные растут — K чувствителен
вдвойне. У здоровой уравновешенной скважины K держится в районе 0.02–0.08.

Регистр 1998 (скорость) **в формулу не входит** — это ворота «привод качает».
Снимки при стоящем станке в перцентили не попадают, иначе K начинает мерить
простои, а не насос.

## Три ветви

| Ветвь | Условие | Зачем |
|---|---|---|
| `abs` | `K >= 0.20` | универсальная граница; глушится, если собственный фоновый P90 выше 0.13 — у хронически неуравновешенных станков 0.2 это обычная жизнь |
| `rel` | `K >= 0.13` и `K >= 1.5 x фонового P90` | тихие скважины: утечка началась с 0.04 и дошла до 0.15 — до абсолютного порога далеко, а рост в разы уже очевиден |
| `loss` | `P95 < 10% фоновой медианы P95` | страховочная: нагрузка рухнула целиком, K вырождается, диагноз ставится по факту «привод крутит пустой станок» |

Фон — собственные последние 60 суток скважины (минимум 10 валидных; сутки
валидны от 100 снимков), строго каузальный. Сутки, вызвавшие тревогу, из фона
последующих исключаются: иначе медленная деградация втягивается в собственный
фон, порог ползёт вслед за ней и правило глушит само себя.

## Жизненный цикл эпизода

Сутки классифицируются на четыре состояния, а не на два — «нет сработки» само
по себе нормой не является:

| Состояние | Когда | Влияние |
|---|---|---|
| `undetermined` | < 100 снимков или фона меньше 10 суток | ничего: ни сработки, ни восстановления |
| `alert` | сработала любая ветвь | открыть / эскалировать / подтвердить |
| `grey` | `0.13 <= K < 0.20`, тревоги нет | рвёт серию восстановления |
| `clean` | `K < 0.13` | копит серию восстановления |

- первые alert-сутки — `warning`, вторые — `alarm` (уровень только растёт);
- закрытие — 4 подряд чистых суток (`recovered`);
- нет валидных суток 14 дней — закрытие как `stale` (станция снята, идёт ПРС).

Латентность: до ~48 ч на `warning` (правило считает только полные сутки, и
переходные сутки обычно молчат — P5 реагирует за час, а P95 падает лишь когда
аномалия покрыла почти все сутки), плюс сутки на `alarm`.

## Расхождения со скриптами прогона

Реализация следует `forward_runner.py` (каузальный форвард), но не буквально:

1. **Разворот uint16** — есть в `forward_runner`, отсутствует в `r9_batch`.
   Без него P5 никогда не станет отрицательным, P95 раздувается до ~64000, и
   правило не срабатывает ни разу. Реализовано в SQL источника. **Отчёт
   ТР4-1 посчитан `r9_batch`, то есть без разворота** — расхождение к автору.
2. **Дедуп снимков** по `savetime` (`DISTINCT ON`): в копии дубли источника
   лежат отдельными строками, а перцентиль считается по набору значений —
   дубль получил бы двойной вес и завысил счётчик валидности суток.
3. **Ветвь `loss` работает и при `P95 <= 0`.** В скрипте такие сутки
   отбрасываются фильтром `k is not None` — то есть самое мёртвое состояние
   молча выпадает из оценки.
4. **Нормализация** — своя: в скриптах эпизод просто кончается, когда
   кончились alert-сутки. Кластеризацию с разрывом до 3 суток заменяет
   гистерезис закрытия (строго консервативнее).
5. **Внутрисуточная ветвь не реализована.** В `r9_batch` она есть (окна по 36
   снимков), но помечена автором как невалидированная — «справочно».

## Чего нет

- **Точность (FPR) не оценена** — ни автором, ни нами. Полнота 97.5% из отчёта
  ТР4-1 получена на выборке, отобранной по исходу, и по **двум** каналам.
- **Канал ГЗУ** (нулевые замеры Qж при работающем СУ) — отдельное правило,
  здесь его нет. По отчёту он даёт первый сигнал в 53 случаях из 119, ещё в
  42 идёт вместе с СУ; чистое СУ — 24.
- **Пороги не перекалиброваны** на нашей копии данных.

## Диагноз

`reason_code = load_imbalance` — наблюдение, а не диагноз. Под одной сработкой
в реестре ТР4-1 лежат и утечка клапанов, и неполное заполнение, и НРН. R9
отвечает «идти смотреть эту скважину?», а не «что везти в ремонт»; уточняют
динамограмма и ГЗУ.
